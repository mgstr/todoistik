The Dashboard — what it can honestly say, and what it should look like

Five panels were asked for. This page settles two things before any of them is built: what the stored record can actually answer, and how much chart vocabulary the app is willing to own. Every specimen is rendered with todoistik's own stylesheet rather than a mockup of it, in both themes, with the same invented week behind all of them.

What the page recommends. Variant D: bars-as-rows for anything that is a list of names, a bare column strip for anything that is a stretch of time, and no third shape. That is one new idea — a proportion drawn as length — used in two orientations, which is as little as a dashboard can be built out of. Every chart carries its own number in words beside it, so nothing on the screen can only be read by eye.

And one thing has to be decided before the third panel can exist at all: the audit log cannot currently tell an inbox item that became an action from one that became a project or a someday item — all three are written down as deleted. See the ledger directly below.

Note 1 — inbound and outbound are not one pipe

One inbox item can become a project with five actions; another is answered by the two-minute rule and becomes nothing at all. So a chart drawing arrivals against completions is drawing two different populations and inviting the eye to subtract them. There are two coherent readings and the app can serve either:

  • The inbox pipe — captured against processed. Both ends are inbox items, the subtraction is real, and the difference is literally the number sitting in the Inbox. This measures the practice: am I emptying what arrives.
  • The work pipe — commitments made against commitments completed (actions and projects, plus the two-minute answers, which are work done without an item ever existing). This measures the load: am I finishing what I take on.

Both are rendered below, stacked, because on inspection they are the two halves of the same question and neither answers for the other. If only one ships, it should be the inbox pipe: it is the one whose two lines belong on the same axis.

Note 2 — "age in the system" has no single answer, and the good one is a duration, not an age

Nothing links an inbox item to the action it became: the item is deleted and a new action is inserted, with no lineage kept (design.md, "Items" — an item is stored as itself). So capture to completion cannot be computed, and no panel should pretend otherwise. What is computable, from the audit log alone:

  • Time in the inbox — capture to decision, by pairing each leaving event with the created entry for the same item_id immediately before it. (Ids are reused after a delete, so it must be the nearest preceding one; an id is live at most once at a time, which makes that exact.) This is the real measure of the practice's speed, and it is already in the record, untouched, going back to the first capture.
  • Time as a commitment — creation to completion, the same pairing on action and project ids.
  • Age of what is open now — a plain read of the live tables, per view. This is what "nothing dies silently" actually asks about, and it is the only one of the three that is about the present.

2. Three whole dashboards, and the mix

Turning numbers into shapes is not a change to one panel, so each variant is rendered as the whole screen — the same five panels, the same data, the rail alongside so the new row can be seen where it lands. A is drawn with the rail; B, C and D drop it to give the panels the width.

A — no chart at all: the dashboard is a list

The starting position, and the one that has to be beaten: the app has no chart vocabulary anywhere today, and "add only functionality I will use" is a design principle. Everything here is a number, a word and a badge — shapes the app already owns.

A · light

A · dark

  • What it gets right. Nothing on it can be misread, it costs no new CSS, and it reads at any width. The seven days as 6 · 9 · 3 · 2 · 11 · 7 · 4 is genuinely legible — seven numbers is under the limit where a row of digits still parses as a shape.
  • Where it fails. The year. A trend over fifty-two weeks is the one thing on this screen that a sentence cannot say: "5.8 a day" is an average with no direction in it, and whether the number has been climbing since March is exactly what the panel was asked for. A also has no way to show one distribution against another — seven sources as seven numbers is a table you have to sort in your head.

B — the bar is the row

Every chart is a list, because a list is the shape this app is made of. A day is a row, a source is a row, and the bar is a fill drawn inside the row it belongs to — the same .row geometry, hover and all, with one new declaration on it. No SVG anywhere.

B · light

B · dark

  • What it gets right. The distributions. A ranked list of names with a length beside each is exactly what "where do captures come from" is, and it arrives already sorted, already labelled, and already able to carry a count and a percentage without a legend. It is also the only variant where a row could later become a link into a filtered view without anything being redesigned.
  • Where it fails. The year again, and worse than A: fifty-two weeks cannot be fifty-two rows, so B has to either drop the long view or borrow a shape from C. Seven days as seven rows also spends a lot of height on very little information, and it turns a week — which is a thing with a left-to-right direction — into a vertical list, which is the one orientation a week does not have.

C — small charts: inline SVG

A column strip for the week, a line for the year, a hundred-percent stacked bar for the distributions. One hue throughout — the accent, at descending opacity — because a second colour in this app already means something (green is a context, red is overdue, purple leaves the app).

C · light

C · dark

  • What it gets right. Time. The week reads as a week, the year reads as a direction, and the dotted mean line answers "is this week normal" without a word being written. This is the only variant that answers the question the two speed panels were actually asked.
  • Where it fails. The stacked bar. Seven sources in one bar needs seven shades of one hue and a legend underneath, and by the time the legend carries every name and every count the bar has become decoration above a table that already said it. It is also the loudest thing in the app by some distance — four charts on one screen, in an app whose every other screen is text.

D — the mix, and the page's recommendation

C's column strip wherever the x axis is time; B's bar-in-a-row wherever it is a list of names; A's discipline on all of it, which is that every chart carries its own number in words. Nothing is drawn that is not also written.

D · light

D · dark

  • The argument. A distribution and a time series are not the same kind of fact, and the two variants that tried to draw both with one shape each failed on the other one. Splitting them costs a second shape and buys both. The two shapes also stay in their lanes with no rule to remember: length along a row for a name, height along a strip for a day.
  • What it deliberately does not have. No axes, no gridlines, no tick labels, no tooltips, no legend except where a stack genuinely needs one, and no second hue. A chart here is an outline of a number that is already written next to it — if the chart vanished, the screen would still say everything.
  • Known trade-off, accepted. The year line has no scale on it, so it says direction and not magnitude. That is the right trade for a panel whose headline figure is the magnitude, and it is why the mean line is drawn: it is the one reference value worth having, and it is labelled.

5. What it would take

  • design.md — a "### Dashboard" section under "Views", and an admission in the "Views" preamble that this one is not a query over items but a count of them, which is the first screen in the app that is neither a list of items nor one item shown in full. Every panel's window needs stating (the week is the last seven days, not the calendar week) and every figure needs its definition beside it, for the same reason the filter line has to confess what it hides: a number whose definition is not on the screen is a number that gets misread once and distrusted afterwards.
  • The audit events — the third panel needs Action, Project and Someday to stop all writing deleted. Beyond the dashboard, the audit log currently says "deleted" about an item that became an action, which is visible on the Audit screen today and is arguably wrong on its own terms. Entries already written stay ambiguous and would have to read as one bucket, which is an argument for doing it sooner.
  • implementation.md — the queries (all of them aggregates over audit_log, which has no index on at or event today), the panel layout, and the new CSS. Note that NavCounts already runs eleven queries per page render; the dashboard's are heavier and must not join that set.
  • keys.md — g d for the view. Free: the taken letters are i t n p k w c s h r a u e z. Nothing else on the screen is pressable, so the Dashboard is the first view with no keys of its own — which is worth saying out loud in that file rather than leaving as a gap.
  • The nav — between Audit and Settings, in the Records group, carrying no badge, like the other three there. A count on it would have nothing to count.

One thing noticed and not acted on: nothing here is reachable from the read API, so an agent asked "is my system keeping up" still cannot answer it. That is a bigger question than this page — the API is "any view, with the caller's own filters", and the Dashboard is not a view in that sense.
