The actionable row, and how deep the question really is

The processing screen's third row — the answers that make something you have to act on. Written out as a sequence of questions it is five deep: action or project, who does it, standalone or filed, existing project or a new one, next action or parked. This page is the argument that it is one question and one form, and the form is live: type into the project box and watch the three states it has.

Where the depth goes

As a sequence of questions

Each step waits for the one above it.

Action or project?
Who does it — me, or someone else?
Standalone, or filed under an outcome?
Which project — and does one exist?
Is it the next action?
no project yet → go and create one, then come back (leaves the screen)
5 questions, up to 4 of them sequential, one detour off the screen.

Separated by kind

Only one of the five is a question.

Does this line name a step, or an outcome? — decides which object is created, cannot be defaulted
Who does it — a field (assignedTo), visible, two states
Where it lives — one field, three states: empty · matched · unmatched-so-create
Next or parked — already settled in design.md: next by default, parking is deliberate
1 question, then 1 form. Two of its fields can be left alone and still be right.

The three that stopped being questions did not stop mattering — they became a field you can see, a field you can leave empty, and a default that design.md already argued for. Nothing was hidden; what was removed is the waiting.

stage 1 The screen, with its third row filled in

Two buttons, in the row the … is holding today. The wording asks the distinction rather than naming the object — “a step” and “an outcome” is the judgement being made; “Action” and “Project” is what it produces.

stage 2 The action form, live

Type in the Project box. Empty means standalone. Matching text picks an active project — the same matcher the name filter uses. Text that matches nothing offers to create it, and only then asks for a definition of done. The green line at the bottom says what pressing the button would actually create, which is the thing worth checking on this page.

Active projects Winter-proof the car · Kitchen renovation · Q3 accounts · Sail licence

stage 2 The project form, two seedings

The same form is reached two ways, and the only difference is which field the captured line landed in. That is what lets “this is an outcome” and “this step has no home yet” be one code path.

“Someone else does it” stops being a top-level branch Listed alongside Action, Project, Trash… It creates the same object as Action with one field set, and that field is equally valid on a project's first action. A branch that differs by a field is a field
A new project can be created from the action branch “an existing active project can be named instead” Otherwise a step whose outcome is not yet tracked has no correct answer here — it becomes standalone and the outcome goes unrecorded
A project's first action can be delegated Silent Already implied — the delegate branch says a delegated action belongs to a project as validly as one you do yourself. Saying it once, on the field, covers both
The first action of a new project cannot be parked “at least one action, which becomes the next action” Not a change — a consequence worth rendering. The park control is absent in the create-a-project state, present when an existing project is picked

Then the keys fall out

With the row settled the screen is six single keystrokes and nothing else: t trash · r reference · 2 two-minute · s someday · a action · p project — plus esc to leave without answering. That is why implementation.md's register parked the keys behind this row rather than adding them first: the row decides how many there are. One thing to settle with them: t is “pick for today” on every list view, and would be “trash” here.
